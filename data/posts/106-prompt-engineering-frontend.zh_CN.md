## 目标

Prompt Engineering 不是产品经理或 AI 研究员的专利。作为前端工程师，你每天都在和 AI 打交道——用 Copilot 写代码、用 ChatGPT 调试 Bug、用 AI 生成组件。但你有没有发现，同样是用 AI，有些人效率是你的 10 倍？差距就在于 Prompt Engineering。本文将从前端工程师的视角，系统性地介绍如何写出更好的 AI 指令。

## 背景

### 前端工程师为什么要学 Prompt Engineering

前端工程师和 Prompt Engineering 之间有着天然的联系：

1. **AI 辅助编码已成标配**：GitHub Copilot、Cursor、Claude Code 等工具已经深度集成到前端工作流中
2. **API 设计思维相通**：设计 Prompt 本质上和设计 API 接口一样——输入什么、输出什么、格式是什么
3. **前端需要理解 AI 输出**：理解 Prompt 能帮助你更好地理解 AI 生成的代码质量
4. **技术写作能力**：清晰的 Prompt 需要清晰的表达，这和写技术文档的能力是一脉相承的

### 为什么大多数人的 Prompt 效果不好

常见的问题模式：

- **太模糊**："帮我写一个登录页面"——结果完全不符合需求
- **太宽泛**："用 React 写一个表单"——没有约束，AI 会给你一个通用方案
- **缺少上下文**：没有告诉 AI 你的项目用的是什么技术栈、有什么约束
- **没有迭代**：一次 Prompt 就期望完美结果，不愿意调整

## Prompt Engineering 核心原则

### 原则一：明确角色和上下文

给 AI 一个清晰的角色定位，它会更准确地理解你的需求：

```markdown
# 差的 Prompt
帮我写一个 React 组件

# 好的 Prompt
你是一位资深 React 开发者，精通 TypeScript 和 Tailwind CSS。
我需要你帮我写一个数据表格组件，要求：
- 支持列排序、筛选、分页
- 使用 TanStack Table v8
- TypeScript 类型严格
- 支持暗色模式
- 移动端响应式
```

### 原则二：提供示例（Few-shot）

AI 通过示例学习的速度远比通过描述快。这和写组件文档一个道理——一个好的示例胜过千言万语。

```markdown
请帮我写一个 `useDebounce` Hook，用法如下：

```typescript
function SearchInput() {
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebounce(query, 300);
  
  useEffect(() => {
    if (debouncedQuery) {
      fetchResults(debouncedQuery);
    }
  }, [debouncedQuery]);

  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}
```

要求：
- 泛型支持
- 支持取消功能
- 返回值类型推断正确
```

### 原则三：分步骤拆解

复杂任务拆解成小步骤，每一步都有明确的输出：

```markdown
我需要你帮我设计一个前端监控系统，请按以下步骤来：

**第一步：需求分析**
- 列出前端监控需要覆盖的核心指标（性能、错误、用户行为）
- 每个指标的数据结构定义

**第二步：数据采集层设计**
- Performance API 的使用方案
- 错误捕获方案（全局错误、Promise 错误、资源加载错误）
- 用户行为追踪方案

**第三步：上报层设计**
- 上报时机（批量上报 vs 实时上报）
- 数据格式和压缩策略
- 失败重试机制

**第四步：前端 SDK 设计**
- 初始化配置
- API 设计
- 插件化架构

请先完成第一步，等我确认后再继续。
```

### 原则四：约束输出格式

告诉 AI 你要什么样的输出格式，避免返工：

```markdown
请帮我写一个 React 组件，输出格式要求：

1. 单个 `.tsx` 文件
2. 使用 TypeScript（strict 模式）
3. 样式使用 Tailwind CSS（不要 styled-components）
4. 使用 React Server Components（标明哪些需要 "use client"）
5. 包含完整的 Props 类型定义
6. 包含 JSDoc 注释
7. 包含至少 3 个使用示例
```

```markdown

- 设计系统：shadcn/ui

- API 层：TanStack Query

- 交互行为

- 必须支持键盘操作

## 高级技巧

### Chain of Thought（思维链）

让 AI 展示推理过程，特别适合复杂问题：

```markdown
请按照以下步骤分析这段代码的性能问题：

1. **识别瓶颈**：这段代码的时间复杂度是多少？空间复杂度呢？
2. **分析原因**：为什么会出现性能问题？是算法问题还是实现问题？
3. **评估影响**：在什么数据量下会出现明显卡顿？
4. **提出方案**：列出 3 种优化方案，比较优缺点
5. **推荐最优解**：选择最适合当前场景的方案，给出完整代码

请一步一步分析，不要跳过中间步骤。
```

### 用 XML 标签结构化 Prompt

```markdown
<task>
  编写一个 React 自定义 Hook
</task>

<context>
  项目使用 React 18 + TypeScript，需要一个管理表单状态的 Hook
</context>

<requirements>
  - 支持多字段
  - 支持校验
  - 支持初始值和重置
  - 类型推断友好
</requirements>

<constraints>
  - 不依赖任何第三方库
  - 不超过 150 行代码
  - 必须有完整的类型定义
</constraints>

<output_format>
  单个 .ts 文件，包含所有类型定义和实现
</output_format>
```

### 迭代优化策略

不要期望一次得到完美结果，迭代是关键：

```markdown
# 第一轮：获取基础方案
请帮我设计一个图片懒加载组件的接口...

# 第二轮：细化需求
方案不错，但我需要补充几个需求：
1. 支持占位图
2. 支持加载失败的 fallback
3. 支持 Intersection Observer 和 scroll 两种模式

# 第三轮：优化细节
代码质量很好，但有几个细节需要调整：
1. 组件命名改为 ImageLoader
2. 需要支持 SSR（服务端渲染时不能使用 IntersectionObserver）
3. 添加 loading="lazy" 作为默认行为

# 第四轮：最终确认
完美！请输出最终版本的完整代码。
```

## 常见误区

### 误区一：过度依赖 AI

AI 是辅助工具，不是替代品。你需要：
- 理解 AI 生成的每一行代码
- 检查 AI 的输出是否符合项目规范
- 对 AI 的建议进行独立判断

### 误区二：忽视上下文窗口限制

每次对话都有 token 限制。策略：
- 单次只讨论一个问题
- 必要时提供精简的上下文
- 使用文件引用而非复制粘贴大量代码

### 误区三：Prompt 越长越好

长度不是关键，清晰度才是。好的 Prompt 应该：
- 每句话都有明确的目的
- 避免重复和冗余
- 用结构化的方式组织信息

## 总结

Prompt Engineering 是前端工程师在 AI 时代的核心竞争力之一。掌握这些原则和技巧：

1. **明确角色和上下文**：给 AI 清晰的定位
2. **提供示例**：用 Few-shot 引导 AI
3. **分步骤拆解**：复杂任务分步处理
4. **约束输出格式**：避免返工
5. **迭代优化**：不期望一次完美

记住，好的 Prompt 和好的代码一样——简洁、清晰、意图明确。把这些技巧融入你的日常工作流，你会发现 AI 工具的效率可以提升数倍。
